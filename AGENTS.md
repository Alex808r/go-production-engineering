# AGENTS.md — Правила работы AI-ассистента в проекте go_course_4

## 1. Безопасность Git и коммитов (КРИТИЧЕСКИ ВАЖНО)
- **СТРОГИЙ ЗАПРЕТ на автоматический коммит и пуш.** Агент НИКОГДА не выполняет `git commit` или `git push` без прямого подтверждения пользователя.
- **Обязательная процедура перед коммитом:**
  1. Выполнить `git status` и `git diff --stat`.
  2. Сформулировать краткое и структурированное сообщение коммита (формат Conventional Commits: `type(scope): description`).
  3. Сделать паузу и явно запросить подтверждение пользователя: «Закоммитить эти изменения?».
  4. Вызывать `git commit` только после получения однозначного согласия пользователя («да», «ок», «коммить»).
- Не создавать новые ветки или Pull Request'ы без прямого указания.

## 2. Доказательства в коде (Code Evidence)
- Любые утверждения о структуре пакетов, сигнатурах функций, типах, поведении микросервисов (`lynks`, `wallet`, `GoSearch`) и учебных модулей (`lessons/`) делать **только на основе реально прочитанного кода** (через чтение файлов или поиск с достаточным контекстом).
- Не делать догадок и предположений по обрывочным фрагментам.

## 3. Приоритет инструкций пользователя
- Пользователь — ведущий архитектор и инженер.
- Прямые указания пользователя буквальны и имеют безусловный приоритет над системными эвристиками или шаблонами IDE.
- Не менять скоуп задачи и не делать незапрошенного рефакторинга соседнего кода.

## 4. Стандарты качества Go и верификация
- **Обязательная проверка кода перед отчетом:**
  - Тесты: `go test ./...` (или целевой пакет `go test -v ./lessons/...`).
  - Проверка конкурентности: `go test -race ./...` для кода с горутинами и каналами.
  - Компиляция: `go build ./...`.
- **Линтинг:** Не запускать автофикс `golangci-lint run --fix` без явного запроса. Устранять замечания точечно.
- **Сторонние утилиты и библиотеки:** Проверять реальные флаги CLI (`protoc`, `goose`, `migrate`, `golangci-lint`) и зависимости в `go.mod`, а не полагаться на память.

## 5. Правила работы с локальной документацией (`go-documentation/`)
- Документация проекта — это 6-томная структурированная база знаний.
- **Синхронизация оглавления:** При добавлении, переименовании или дроблении глав обязательно обновлять центральное оглавление и якоря в `go-documentation/README.md`.
- **Единое место хранения:** Не создавать отдельных `.md` файлов в корне репозитория (кроме конфигурационных `AGENTS.md` / `README.md`). Все руководства и памятки размещать строго в `go-documentation/`.
- **Сохранение целостности:** Сохранять существующие docstrings, комментарии в `.go` файлах и разметку GitHub Alerts (`> [!TIP]`, `> [!IMPORTANT]`, Mermaid).

## 6. Что НЕ делать автоматически
- НЕ коммитить и НЕ пушить без прямого подтверждения.
- НЕ запускать автофикс линтеров без запроса.
- НЕ удалять комментарии и документацию разработчика.
- НЕ использовать эмодзи в именах функций Go, переменных, типах и текстах коммитов.

## 7. Частые грабли Go (держать в фокусе)
- **Интерфейсный nil:** возвращать нетипизированный `nil`, а не пустой указатель `(*MyErr)(nil)` во избежание `err != nil == true`.
- **Затенение (Shadowing):** внимательно проверять повторное использование `:=` во вложенных блоках `if`/`for`.
- **Утечки горутин:** всегда гарантировать вызов `cancel()` у контекстов (`defer cancel()`) и гарантировать вычитку каналов.
- **Гонки в Map:** помнить, что стандартный `map` в Go не потокобезопасен (использовать `sync.Mutex` / `sync.RWMutex` или `sync.Map`).
