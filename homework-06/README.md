## Задача №1: Идиоматичный рефакторинг геометрии (`pkg/geom`)

### Исходный код (`06-oop/5-hw/hw.go`):
```go
type Geom struct {
    X1, Y1, X2, Y2 float64
}

func (geom Geom) CalculateDistance() (distance float64) {
    if geom.X1 < 0 || geom.X2 < 0 || geom.Y1 < 0 || geom.Y2 < 0 {
        fmt.Println("Координаты не могут быть меньше нуля")
        return -1
    } else {
        distance = math.Sqrt(math.Pow(geom.X2-geom.X1, 2) + math.Pow(geom.Y2-geom.Y1, 2))
    }
    // возврат расстояния между точками
    return distance
}
```

### Перечень исправленных недостатков:

1. **Имя получателя метода (Receiver Name):**
   - *Было:* `func (geom Geom)` — избыточное дублирование названия типа.
   - *Стало:* `func (g Geom)` / `func (p Point)` — в Go (согласно *Go Code Review Comments: Receiver Names*) ресивер должен состоять из 1-2 букв, отражающих тип. Запрещены слова `this`, `self`, `me` и длинные имена.
2. **Именование метода (Method Naming):**
   - *Было:* `CalculateDistance()` — лишний глагол `Calculate...`.
   - *Стало:* `Distance()` — согласно *Effective Go*, свойства и вычисляемые характеристики объекта именуются лаконичными существительными (`Distance()`, `Area()`, `Length()`).
3. **Побочные эффекты (Side Effects / `fmt.Println`):**
   - *Было:* Вызов `fmt.Println` внутри чистой математической функции библиотеки.
   - *Стало:* Удален консольный вывод. Библиотечные пакеты не должны загрязнять `os.Stdout` вызывающего кода.
4. **Математическая некорректность и "магические числа":**
   - *Было:* Запрет отрицательных координат (`< 0`) и возврат `-1`.
   - *Стало:* В декартовой системе координат отрицательные оси абсолютно валидны, а расстояние между любыми точками $\sqrt{\Delta X^2 + \Delta Y^2}$ всегда строго $\ge 0$.
5. **Неэффективность вычислений (`math.Pow`):**
   - *Было:* `math.Pow(..., 2)` — медленное возведение в степень через логарифмические аппроксимации.
   - *Стало:* Использование стандартной высокоточной функции `math.Hypot(dx, dy)`, оптимизированной на уровне ассемблера и защищающей от переполнения (`overflow/underflow`).
6. **Избыточный `else` после `return`:**
   - *Было:* Ветвление `if ... return -1 } else { ... }`.
   - *Стало:* Идиома *Guard Clause / Early Return* — код выровнен по левому краю без лишних отступов.
7. **Именованный результат и лишние переменные:**
   - *Было:* `(distance float64)`, ручное присваивание `distance = ...` и возврат.
   - *Стало:* Прямой чистый возврат `return math.Hypot(target.X-p.X, target.Y-p.Y)`.
8. **Объектная декомпозиция (ООП в стиле Go):**
   - *Было:* Монолитная структура `Geom` с четырьмя координатами смешивала точку и отрезок.
   - *Стало:* Выделен атомарный тип `Point{X, Y float64}` с методом `Distance(target Point)`. Для обратной совместимости сохранена структура `Geom` с делегированием вызова точкам.

## Задача №2: ООП-архитектура поискового движка GoSearch

Согласно слайдам 24 и 26:
- *«Если пакет предназначен для описания некоторой сущности, которая хранит и изменяет своё состояние между вызовами методов из других пакетов, то нужно использовать ООП-стиль.»*
- *«Лично я предпочитаю инициализировать зависимости на верхнем уровне системы – объект сервер – и передавать их при необходимости в конструкторы подсистем.»*

### Реализация:

1. Создан пакет `pkg/engine` с типом `Engine`:
   ```go
   type Engine struct {
       crawler crawler.Interface
       index   *index.Service
       docs    []crawler.Document
   }
   ```
2. Конструктор `New(cr crawler.Interface, idx *index.Service) *Engine` принимает абстрактные зависимости, созданные в `main.go`.
3. Методы объекта:
   - `eng.Scan(urls []string, depth int) error` — сканирование и индексация.
   - `eng.Search(query string) []crawler.Document` — поиск через обратный индекс и бинарный поиск.
   - `eng.Save(w io.Writer) error` — сохранение состояния в поток.
   - `eng.Load(r io.Reader) error` — загрузка состояния из потока.
