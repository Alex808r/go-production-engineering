## 1. Ментальная модель: Контейнеризация простыми словами

Главная проблема в разработке звучит так: *«На моем компьютере всё работало, а на сервере упало!»*. Причина — разница в версиях системных библиотек, операционных систем, установленных пакетов и переменных окружения.

**Контейнеризация** решает эту проблему раз и навсегда: приложение упаковывается вместе со всеми его зависимостями в изолированный самодостаточный контейнер, который одинаково работает на macOS, Ubuntu, Windows или в облаке AWS/Kubernetes.

---

### 1.1. Виртуальные машины vs Контейнеры

```
┌─────────────────────────────────┐       ┌─────────────────────────────────┐
│     ВИРТУАЛЬНАЯ МАШИНА (VM)     │       │       КОНТЕЙНЕР (DOCKER)        │
├────────────────┬────────────────┤       ├────────────────┬────────────────┤
│ Приложение А   │ Приложение Б   │       │ Приложение А   │ Приложение Б   │
├────────────────┼────────────────┤       ├────────────────┼────────────────┤
│ Библиотеки (OS)│ Библиотеки (OS)│       │ Библиотеки     │ Библиотеки     │
├────────────────┼────────────────┤       ├────────────────┴────────────────┤
│ Гостевая ОС A  │ Гостевая ОС Б  │       │       Движок Docker Engine      │
│ (Linux/Windows)│ (Linux/Windows)│       │   (Изолированные процессы)      │
├────────────────┴────────────────┤       ├─────────────────────────────────┤
│     Гипервизор (VirtualBox/KVM) │       │   Единое ядро ОС хоста (Linux)  │
├─────────────────────────────────┤       ├─────────────────────────────────┤
│        Железо (CPU, RAM)        │       │        Железо (CPU, RAM)        │
└─────────────────────────────────┘       └─────────────────────────────────┘
```

| Критерий | Виртуальная машина (VM) | Контейнер Docker |
| :--- | :--- | :--- |
| **Уровень изоляции** | Аппаратный (эмуляция всего железа) | Уровень ядра ОС (изоляция процессов) |
| **Операционная система** | Каждая ВМ запускает свою полноценную гостевую ОС | Все контейнеры делят одно общее ядро хоста |
| **Размер** | Десятки гигабайт (образ ОС + диск) | От 10 до 100 мегабайт |
| **Скорость запуска** | 1–3 минуты (загрузка ядра ОС) | **10–100 миллисекунд** (старт обычного процесса) |
| **Накладные расходы** | Высокие (память и CPU тратятся на гостевую ОС) | **Околонулевые** (как у нативного процесса) |

---

### 1.2. Внутреннее устройство: cgroups и namespaces ядра Linux

Контейнер — это **не** виртуальная машина. На самом деле внутри Linux контейнер — это **обычный процесс хоста**, ограниченный двумя встроенными механизмами ядра Linux:

1. **Linux Namespaces (Пространства имен — Изоляция видимости):**
   * `pid`: процесс видит только свои дочерние процессы (внутри контейнера наш сервис имеет PID 1).
   * `net`: свой собственный виртуальный сетевой интерфейс, таблица маршрутизации и локальные порты.
   * `mnt`: своя изолированная файловая система (процесс не видит файлов хоста).
   * `ipc`: изоляция межпроцессного взаимодействия.
   * `user`: отображение внутренних UID на внешние безопасные UID.
2. **Control Groups (`cgroups` — Ограничение ресурсов):**
   * Задают строгие лимиты: сколько оперативной памяти (например, `max 512MB`) и процессорного времени (`1.5 CPU`) разрешено потреблять данному процессу. При превышении памяти ядро Linux присылает `OOM Killer` (Out Of Memory).

> 💡 **Как это работает на macOS и Windows?**  
> Поскольку у macOS и Windows другое ядро (XNU и Windows NT), Docker Desktop прозрачно запускает крошечную виртуальную машину на базе облегченного дистрибутива Linux (Alpine Linux), внутри которой крутятся контейнеры.

### 1.3. Четыре столпа Docker: Рецепт, Слепок, Процесс и Реестр

```mermaid
flowchart TD
    Dockerfile["<b>1. Dockerfile</b><br/>Текстовый рецепт"]
    Image["<b>2. Image / Образ</b><br/>Неизменяемый слепок"]
    Container["<b>3. Container</b><br/>Запущенный процесс"]
    Registry["<b>4. Registry / Docker Hub</b><br/>Облачное хранилище"]

    Dockerfile -->|"docker build"| Image
    Image -->|"docker run"| Container
    Image <-->|"docker push / pull"| Registry

    style Dockerfile fill:#2c3e50,stroke:#34495e,stroke-width:3px,color:#fff
    style Image fill:#3498db,stroke:#2980b9,stroke-width:2px,color:#fff
    style Container fill:#27ae60,stroke:#229954,stroke-width:2px,color:#fff
    style Registry fill:#f39c12,stroke:#d68910,stroke-width:2px,color:#000
```

1. **`Dockerfile` (Рецепт):** текстовый файл с пошаговыми инструкциями по сборке окружения.
2. **`Image` / Образ (Слепок):** неизменяемый архив (snapshot), состоящий из слоев (layers). Содержит файловую систему, зависимости и скомпилированный бинарник.
3. **`Container` (Контейнер):** живой запущенный процесс, созданный из образа. Поверх неизменяемых слоев образа накладывается тонкий перезаписываемый слой (Read-Write Layer).
4. **`Registry` (Реестр):** хранилище образов (как GitHub для кода, так Docker Hub / GitHub Container Registry для Docker-образов).

## 2. Шпаргалка по CLI-командам Docker

### Запуск и управление контейнерами
```bash
# Запустить контейнер в фоновом режиме (-d) с пробросом порта (-p) и именем (--name)
docker run -d -p 5432:5432 --name postgres-dev -e POSTGRES_PASSWORD=secret postgres:16-alpine

# Посмотреть активные запущенные контейнеры
docker ps

# Посмотреть ВСЕ контейнеры (включая остановленные и завершившиеся с ошибкой)
docker ps -a

# Посмотреть логи контейнера в реальном времени (follow)
docker logs -f postgres-dev

# Войти внутрь работающего контейнера в интерактивный терминал (bash/sh)
docker exec -it postgres-dev sh

# Остановить контейнер (отправляет сигнал SIGTERM, затем через 10с SIGKILL)
docker stop postgres-dev

# Удалить остановленный контейнер
docker rm postgres-dev

# Принудительно остановить и сразу удалить контейнер
docker rm -f postgres-dev
```

### Управление образами
```bash
# Собрать образ из Dockerfile в текущей папке (.) с тегом my-app:latest
docker build -t my-app:latest .

# Список локально скачанных и собранных образов
docker images

# Удалить неиспользуемый образ
docker rmi my-app:latest

# Скачать готовый образ из Docker Hub
docker pull redis:7-alpine
```

### Мониторинг и очистка диска
```bash
# Потребление ресурсов контейнерами в реальном времени (CPU, RAM, Network I/O)
docker stats

# Детальная JSON-информация о контейнере или томе
docker inspect postgres-dev

# 🧹 СПАСЕНИЕ МЕСТА НА ДИСКЕ: удалить все неиспользуемые контейнеры, сети и "висячие" образы
docker system prune -f

# Полная генеральная очистка (включая неиспользуемые тома данных)
docker system prune -a --volumes
```

## 3. Хранение данных (Volumes) и Сети (Networks)

### 3.1. Эфемерность контейнеров и типы томов

Контейнеры по своей природе **эфемерны (stateless)**: если контейнер с базой данных упадет или будет удален, все записанные в него файлы **исчезнут навсегда**, потому что записываемый слой контейнера уничтожается вместе с ним.

Для долговременного хранения данных (**stateful**) используются **Тома (Volumes)**:

```
┌─────────────────────────────────┐
│     КОНТЕЙНЕР (POSTGRESQL)      │
│  /var/lib/postgresql/data       │
└────────────────┬────────────────┘
                 │ Монтирование
                 ▼
┌─────────────────────────────────┐
│    ФАЙЛОВАЯ СИСТЕМА ХОСТА       │
│  /var/lib/docker/volumes/...    │
└─────────────────────────────────┘
```

#### 3 способа монтирования данных:
1. **Named Volumes (Именованные тома — Рекомендуется для баз данных):**
   * `docker run -v pgdata:/var/lib/postgresql/data postgres`
   * Docker сам управляет папкой на хосте. Данные переживают удаление и пересоздание контейнера.
2. **Bind Mounts (Монтирование конкретной папки с хоста — Рекомендуется для конфигов и кода):**
   * `docker run -v $(pwd)/config.env:/app/config.env:ro my-app`
   * Файл или директория с вашего компьютера напрямую пробрасывается в контейнер. Флаг `:ro` делает его доступным только для чтения.
3. **tmpfs Mount (В оперативной памяти):**
   * Данные хранятся только в RAM хоста и никогда не пишутся на диск (для секретов или сверхбыстрых временных буферов).

---

### 3.2. Сетевое взаимодействие и встроенный DNS

Docker имеет встроенный легковесный DNS-сервер:
* Если контейнеры запущены в **одной пользовательской сети** (User-Defined Bridge Network), они обращаются друг к другу **по имени контейнера или имени сервиса**.
* Вам больше не нужно узнавать динамические IP-адреса:
  ```bash
  # Сервис бэкенда подключается к базе просто по строке:
  postgres://user:pass@postgres:5432/db
  ```
* Docker сам разрешит имя `postgres` во внутренний IP-адрес нужного контейнера.

## 4. Анатомия `Dockerfile`: Создание своего первого образа

### 4.1. Ключевые директивы

| Директива | Назначение | Пример |
| :--- | :--- | :--- |
| `FROM` | Базовый образ, от которого наследуемся | `FROM golang:1.24-alpine` |
| `WORKDIR` | Задает текущую рабочую директорию внутри контейнера | `WORKDIR /app` |
| `COPY` | Копирует файлы с хоста внутрь контейнера | `COPY go.mod go.sum ./` |
| `RUN` | Выполняет команду на этапе сборки образа | `RUN go mod download` |
| `ENV` | Задает переменную окружения | `ENV PORT=8080` |
| `EXPOSE` | Документирует порт, на котором слушает процесс | `EXPOSE 8080` |
| `USER` | Переключает пользователя для запуска команд | `USER appuser` |
| `ENTRYPOINT`| Фиксированная неизменяемая команда старта | `ENTRYPOINT ["/app/server"]` |
| `CMD` | Аргументы по умолчанию для `ENTRYPOINT` | `CMD ["--config", "prod.env"]` |

---

### 4.2. Разница между `CMD` и `ENTRYPOINT`

* **`ENTRYPOINT`** — определяет саму исполняемую программу. Ее сложно переопределить при вызове `docker run`.
* **`CMD`** — определяет аргументы по умолчанию, передаваемые в `ENTRYPOINT`. Их легко переопределить в консоли:
  ```dockerfile
  ENTRYPOINT ["/bin/app"]
  CMD ["--port=8080"]
  ```
  Если запустить:
  * `docker run my-app` $\rightarrow$ выполнится `/bin/app --port=8080`.
  * `docker run my-app --port=9090` $\rightarrow$ аргумент `CMD` перезапишется, выполнится `/bin/app --port=9090`.

---

### 4.3. Кэширование слоев: как ускорить сборку в 10 раз

Каждая инструкция в `Dockerfile` создает **новый неизменяемый слой**. Docker кэширует слои: если команда и входные файлы не менялись, слой берется мгновенно из кэша.

#### ❌ Плохая практика (сборка ломает кэш при каждой строчке кода):
```dockerfile
COPY . .                  # Меняется любой .go файл -> кэш сбрасывается!
RUN go mod download       # Каждый раз заново качает 200 МБ библиотек из интернета!
RUN go build -o app .
```

#### ✅ Эталонная практика (кэширование зависимостей):
```dockerfile
# 1. Копируем ТОЛЬКО файлы манифестов библиотек:
COPY go.mod go.sum ./
# 2. Скачиваем библиотеки. Этот слой переиспользуется всегда, пока вы не добавили новую либу!
RUN go mod download

# 3. Копируем сам код приложения. Пересобирается только этот быстрый шаг:
COPY . .
RUN go build -o app .
```

## 5. Multi-Stage Build в Go: Сжатие образа с 1 ГБ до 15 МБ

В традиционных языках (Node.js, Python) для работы в проде нужен интерпретатор и папка `node_modules`.  
Но **Go компилируется в единый самодостаточный машинный бинарник**! В продакшене не нужен ни Go SDK (600 МБ), ни компилятор, ни git, ни исходный код.

Для этого используется **Многоэтапная сборка (Multi-stage build)**:

```mermaid
flowchart TD
    subgraph Stage1 ["Этап 1: Сборка (golang:alpine ~800 MB)"]
        A["Исходный код Go"] --> B["Компилятор go build"]
        B --> C["Бинарник /bin/wallet-app"]
    end
    subgraph Stage2 ["Этап 2: Финальный образ (alpine:3.20 ~15 MB)"]
        C -- "COPY --from=builder" --> D["/app/wallet-app"]
        E["config.env + migrations"] --> D
    end
    Stage2 --> F["Финальный легкий образ для деплоя"]
```

---

### 5.1. Эталонный продакшен-шаблон Dockerfile

```dockerfile
# syntax=docker/dockerfile:1.4
# Включает современный движок BuildKit (поддержка монтирования кэша зависимостей)

# ==============================================================================
# Этап 1: Сборщик (Builder)
# ==============================================================================
FROM golang:1.24-alpine AS builder

WORKDIR /app

# Устанавливаем git и корневые сертификаты (необходимы для скачивания приватных/HTTPS пакетов)
RUN apk add --no-cache git ca-certificates

# 1. Сначала копируем только файлы зависимостей
COPY go.mod go.sum ./

# 2. Скачиваем модули с использованием BuildKit-кэша (/go/pkg/mod).
# Даже при повторной сборке или изменении кода пакеты не будут скачиваться заново из сети!
RUN --mount=type=cache,target=/go/pkg/mod \
    go mod download

# 3. Копируем исходный код приложения
COPY . .

# Переменные целевой платформы (автоматически заполняются при кросс-сборке docker buildx)
ARG TARGETOS
ARG TARGETARCH

# 4. Компилируем полностью автономный статический бинарник:
# - --mount=type=cache для кэша компилятора Go ускоряет инкрементальные сборки в разы
# - CGO_ENABLED=0   : сборка без CGO для работы в минимальном Alpine/Scratch
# - -trimpath       : вырезает абсолютные пути сборщика из стек-трейсов (безопасность + размер)
# - -ldflags="-s -w": вырезает отладочные символы и DWARF, сокращая размер файла в 2–3 раза
RUN --mount=type=cache,target=/go/pkg/mod \
    --mount=type=cache,target=/root/.cache/go-build \
    CGO_ENABLED=0 GOOS=${TARGETOS:-linux} GOARCH=${TARGETARCH:-amd64} go build \
    -trimpath \
    -ldflags="-s -w" \
    -o /bin/wallet-app ./cmd/app

# ==============================================================================
# Этап 2: Минимальный рантайм (Runtime)
# ==============================================================================
FROM alpine:3.20

WORKDIR /app

# ca-certificates нужны для исходящих HTTPS-запросов (внешние API, платежи, webhook)
# tzdata необходима для time.LoadLocation("Europe/Moscow")
RUN apk add --no-cache ca-certificates tzdata

# Безопасность: создаем группу и непривилегированного пользователя с фиксированным UID/GID
RUN addgroup -g 10001 -S appgroup && \
    adduser -u 10001 -S appuser -G appgroup

# Копируем бинарник и файлы миграций, СРАЗУ назначая владельцем appuser через --chown
COPY --chown=appuser:appgroup --from=builder /bin/wallet-app /app/wallet-app
COPY --chown=appuser:appgroup migrations /app/migrations

# ⚠️ ВАЖНО ПО БЕЗОПАСНОСТИ:
# Никогда НЕ зашивайте реальный файл config.env в образ через COPY!
# Секреты и настройки должны передаваться снаружи (через env_file в compose или K8s Secrets).

# Переключаемся на непривилегированного пользователя
USER appuser:appgroup

# Документируем порт сервиса
EXPOSE 8080

# Встроенный опрос здоровья сервиса (использует легковесный wget из busybox)
HEALTHCHECK --interval=10s --timeout=3s --retries=3 --start-period=5s \
    CMD wget --no-verbose --tries=1 --spider http://localhost:8080/health || exit 1

# Форма JSON (exec form) обязательна: процесс получает PID 1 и корректно ловит SIGTERM
ENTRYPOINT ["/app/wallet-app"]
```

Без файла `.dockerignore` команда `COPY . .` скопирует внутрь образа тяжелую папку `.git` (сотни МБ истории коммитов), локальные бинарники с вашего Mac/Windows, а также секретные `.env` файлы!

### 5.3. Флаги компиляции для статического бинарника в продакшене

1. **`CGO_ENABLED=0`**:
   * По умолчанию компилятор Go может динамически связываться с системной Си-библиотекой (`libc/glibc`).
   * В минимальных дистрибутивах (Alpine использует альтернативную `musl libc`, а в `scratch` библиотек нет вовсе) динамический бинарник упадет при старте с ошибкой: `exec /app/wallet-app: no such file or directory`!
   * `CGO_ENABLED=0` делает бинарник полностью автономным — он запустится на абсолютно любом ядре Linux.
2. **`-trimpath`**:
   * Удаляет абсолютные пути исходных файлов из скомпилированного бинарника (например, `/app/cmd/app/main.go` заменяется на относительный `cmd/app/main.go`).
   * Предотвращает утечку информации о структуре папок файловой системы сборочного контейнера и делает стек-трейсы компактными.
3. **`-ldflags="-s -w"`**:
   * `-s`: strip (удаляет таблицу символов программы).
   * `-w`: вырезает метаданные отладчика DWARF.
   * Не влияет на скорость выполнения, но уменьшает бинарник с 35 МБ до 10–12 МБ.
4. **`GOOS=${TARGETOS:-linux} GOARCH=${TARGETARCH:-amd64}`**:
   * Позволяет прозрачно компилировать под архитектуру целевого сервера при сборке на Apple Silicon (M1/M2/M3/M4) или в CI/CD матрицах.

### 5.4. Безопасность: отказ от root-пользователя (`Non-Root Container`)

По умолчанию Docker выполняет команды внутри контейнера из-под пользователя `root` (UID 0).  
Если злоумышленник найдет уязвимость в веб-сервере (например, RCE) и выполнит произвольный код, он может попытаться сбежать из контейнера на хост-машину с правами суперпользователя хоста!

Директива:
```dockerfile
RUN addgroup -g 10001 -S appgroup && \
    adduser -u 10001 -S appuser -G appgroup
USER appuser:appgroup
```
Переключает процесс на изолированного непривилегированного пользователя `appuser` (UID 10001), блокируя возможность модифицировать системные файлы контейнера и хоста. Права на скопированные файлы отдаются сразу через `COPY --chown=appuser:appgroup ...`.

## 6. Docker Compose: Оркестрация мультиконтейнерного стека

### 6.1. Зачем нужен Compose

В боевом проекте у вас всегда несколько компонентов:
* Бэкенд на Go;
* База данных PostgreSQL;
* Кэш Redis;
* Брокер сообщений Apache Kafka.

Чтобы не писать 4 длинные команды `docker run` с кучей портов, сетей и паролей, конфигурация описывается в одном декларативном файле `docker-compose.yml`.

---

### 6.2. Синтаксис `docker-compose.yml`

```yaml
services:      # Перечисление контейнеров
  service-name:
    image:     # Готовый образ из Docker Hub ИЛИ
    build:     # Инструкция сборки своего Dockerfile
    ports:     # "порт_хоста:порт_контейнера"
    volumes:   # Тома для сохранения данных
    env_file:  # Файл с переменными (.env / config.env)
    depends_on:# Порядок запуска
```

> ⚠️ **Поле `version:` больше не нужно:**  
> В современных версиях Docker Compose (Compose V2, запускается через `docker compose` без дефиса) строка `version: '3.8'` считается устаревшей и выдает предупреждение. Пишите сразу с `services:`.

---

### 6.3. Золотой стандарт: `depends_on` + `condition: service_healthy`

Типичная ошибка:
```yaml
depends_on:
  - postgres
```
Docker запустит контейнер PostgreSQL и **мгновенно** следом запустит Go-приложение. Но сервер Postgres запускается несколько секунд (инициализирует страницы памяти, читает WAL-логи).  
В итоге Go-сервис сразу падает с ошибкой: `dial tcp 127.0.0.1:5432: connect: connection refused`.

#### Правильное решение:
Настроить `healthcheck` у базы данных и ждать именно статуса готовности (`service_healthy`):
```yaml
app:
  depends_on:
    postgres:
      condition: service_healthy
```

---

### 6.4. Готовый боевой шаблон: Go App + PostgreSQL 16 + Redis

```yaml
services:
  # ----------------------------------------------------------------------------
  # 1. PostgreSQL 16
  # ----------------------------------------------------------------------------
  postgres:
    image: postgres:16-alpine
    container_name: dev-postgres
    restart: unless-stopped
    env_file:
      - config.env
    environment:
      POSTGRES_DB: ${DB_NAME:-app_db}
      POSTGRES_USER: ${DB_USER:-app_user}
      POSTGRES_PASSWORD: ${DB_PASSWORD:-app_password}
    ports:
      - "${DB_PORT:-5432}:5432"
    volumes:
      - pgdata:/var/lib/postgresql/data
      - ./migrations:/docker-entrypoint-initdb.d:ro
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${DB_USER:-app_user} -d ${DB_NAME:-app_db}"]
      interval: 3s
      timeout: 3s
      retries: 10
      start_period: 3s
    command: >
      postgres
      -c max_connections=200
      -c shared_buffers=256MB
    networks:
      - app-network

  # ----------------------------------------------------------------------------
  # 2. Redis 7
  # ----------------------------------------------------------------------------
  redis:
    image: redis:7-alpine
    container_name: dev-redis
    restart: unless-stopped
    ports:
      - "6379:6379"
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 3s
      timeout: 3s
      retries: 5
    networks:
      - app-network

  # ----------------------------------------------------------------------------
  # 3. Go Application
  # ----------------------------------------------------------------------------
  app:
    build:
      context: .
      dockerfile: Dockerfile
    container_name: dev-app
    restart: unless-stopped
    env_file:
      - config.env
    ports:
      - "${APP_PORT:-8080}:8080"
    depends_on:
      postgres:
        condition: service_healthy
      redis:
        condition: service_healthy
    networks:
      - app-network

volumes:
  pgdata:
    driver: local

networks:
  app-network:
    driver: bridge
```

## 7. Топ-10 типовых ошибок и их устранение (Troubleshooting)

### 1. `bind: address already in use` (Порт занят)
* **Причина:** На вашей хост-машине уже запущен локальный Postgres или Redis на том же порту (5432 или 6379).
* **Решение:** Либо остановите локальную службу (`brew services stop postgresql`), либо измените внешний порт в Compose: `ports: ["5433:5432"]` (хост будет стучаться в 5433, а внутри контейнера останется 5432).

### 2. `connect: connection refused`
* **Причина:** Приложение попыталось обратиться к базе данных до завершения ее инициализации.
* **Решение:** Используйте `depends_on: postgres: condition: service_healthy` вместе с проверкой `pg_isready`.

### 3. Данные в БД стерлись после `docker compose down`
* **Причина:** Использовали команду с флагом `-v` (`docker compose down -v`), который предписывает Docker удалить именованные тома (`volumes`).
* **Решение:** Для штатной остановки без потери данных выполняйте `docker compose down` (без флага `-v`).

### 4. `exec /app/server: no such file or directory`
* **Причина:** Бинарник Go скомпилирован с динамической линковкой под glibc (например, на Ubuntu), а запущен внутри Alpine (где используется `musl libc`).
* **Решение:** Всегда компилируйте статический бинарник: `CGO_ENABLED=0 GOOS=linux go build ...`.

### 5. `time.LoadLocation: unknown time zone Europe/Moscow`
* **Причина:** В минимальном образе `alpine` или `scratch` отсутствует системная база часовых поясов IANA.
* **Решение:** Либо добавьте в образ пакет: `RUN apk add --no-cache tzdata`, либо импортируйте в Go пустой пакет: `import _ "time/tzdata"`.

### 6. База данных стартует, но пароль не подходит
* **Причина:** Вы изменили `POSTGRES_PASSWORD` в `.env`, но папка `pgdata` уже была создана ранее. Postgres применяет пароль суперпользователя **только один раз** при создании пустой базы!
* **Решение:** Удалите старый том: `docker compose down -v`, после чего запустите заново.

### 7. Приложение пытается подключиться к `localhost:5432` из контейнера и падает
* **Причина:** Внутри контейнера `localhost` указывает **на сам этот контейнер**, а не на ваш компьютер или соседний контейнер!
* **Решение:** Указывайте имя сервиса из `docker-compose.yml`: хост базы равен `postgres` (например, `DB_HOST=postgres`).

### 8. `no space left on device`
* **Причина:** Docker накопил гигабайты старых промежуточных слоев и неиспользуемых образов.
* **Решение:** Выполните очистку: `docker system prune -a`.

### 9. Медленная сборка Dockerfile
* **Причина:** На этапе сборки копируются лишние локальные файлы (папка `.git`, временные бинарники, файлы ОС).
* **Решение:** Создайте файл `.dockerignore` и добавьте в него:
  ```text
  .git
  .idea
  .vscode
  bin/
  *.log
  ```

### 10. `permission denied` при записи в volume
* **Причина:** Контейнер запущен от непривилегированного пользователя `appuser` (UID 1000), а папка на хосте принадлежит `root`.
* **Решение:** Убедитесь, что монтируемая директория имеет соответствующие права доступа (`chown -R 1000:1000 ./my-data`).

## 8. Топ-9 вопросов и ответов по Docker для Go-разработчика (Interview & Production FAQ)

### ❓ 1. В чём разница между `scratch`, `alpine` и `distroless`? Какой базовый образ выбрать для Go?

В отличие от Node.js или Python, Go генерирует самодостаточный бинарник, которому не нужен предустановленный язык. Доступны 3 варианта:

| Образ | Размер | Шелл (`sh`) | SSL-сертификаты | Менеджер пакетов | Для чего подходит |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **`scratch`** | **0 МБ** | ❌ Нет | ❌ Нет (нужно копировать) | ❌ Нет | Максимальный минимализм, когда вообще ничего кроме бинарника не нужно. Нельзя сделать `docker exec` и нет утилит для `HEALTHCHECK`. |
| **`alpine`** | **~7 МБ** | ✅ Есть | ✅ Ставятся через `apk` | ✅ `apk` | **Золотой стандарт индустрии для 90% проектов.** Есть шелл для отладки, легко поставить `ca-certificates`, `tzdata` и использовать `wget` в healthcheck. |
| **`distroless`**<br>(Google) | **~2–3 МБ** | ❌ Нет | ✅ Встроены | ❌ Нет | **Максимальная безопасность (Fintech, PCI-DSS).** Образ `gcr.io/distroless/static-debian12:nonroot` уже содержит сертификаты, tzdata и пользователя `nonroot`, но в нем физически нет шелла и утилит, что делает невозможным выполнение произвольных команд злоумышленником. |

### ❓ 2. Почему в `ENTRYPOINT` обязательно использовать JSON-синтаксис `["/app/app"]` (Exec Form)? Как это связано с Graceful Shutdown?

В Dockerfile есть две формы записи команд:
1. **Shell Form:** `ENTRYPOINT /app/wallet-app`  
   Docker запускает бинарник через командную оболочку: `/bin/sh -c "/app/wallet-app"`. В этом случае процесс `/bin/sh` получает **PID 1**, а ваше Go-приложение — дочерний PID (например, 7).
2. **Exec Form (JSON):** `ENTRYPOINT ["/app/wallet-app"]`  
   Бинарник запускается напрямую операционной системой и получает **PID 1**.

> 🚨 **Почему это критично:**  
> При вызове `docker stop` или рестарте пода в Kubernetes контейнеру отправляется сигнал **`SIGTERM`**.  
> Оболочка `/bin/sh` **не пересылает сигналы дочерним процессам**. В результате ваше Go-приложение даже не узнает, что сервер останавливают. Оно не успеет корректно закрыть транзакции в базе данных, сбросить буферы и завершить сетевые подключения. По истечении 10 секунд Docker принудительно убьет сервис сигналом **`SIGKILL`** (`kill -9`) с потерей данных!  
> **Всегда используйте только Exec Form: `ENTRYPOINT ["/app/wallet-app"]`**.

### ❓ 3. Как Go-рантайм видит ограничения CPU в контейнере? Проблема `GOMAXPROCS` и CFS Quota

По умолчанию функция `runtime.NumCPU()` в Go возвращает **общее число физических ядер на материнской плате хост-сервера**, полностью игнорируя лимиты Docker!

* **Сценарий катастрофы:**  
  Ваш сервер имеет 64 CPU. Вы запускаете контейнер и ограничиваете его в compose: `cpus: 2`.  
  Рантайм Go видит 64 ядра и запускает **64 системных потока $M$** планировщика GMP. Linux-планировщик (CFS) видит, что контейнер с лимитом в 2 ядра пытается задействовать ресурсы 64 потоков, и начинает жестко троттлить процесс (**CFS Throttling**). Отклик API (latency) подскакивает с 5 мс до 1500 мс!
* **Решение в проде:**  
  Подключите популярную библиотеку от Uber, которая считывает лимиты из `cgroups` и автоматически задает корректный `GOMAXPROCS`:
  ```go
  import _ "go.uber.org/automaxprocs"
  ```

### ❓ 4. Почему сервис падает с кодом 137 (`OOMKilled`) и как помогает переменная `GOMEMLIMIT`?

До версии Go 1.19 сборщик мусора (GC) ориентировался исключительно на процентный рост кучи (`GOGC=100` — удваивать кучу перед сборкой). GC понятия не имел, что сервис заперт в контейнере с ограничением памяти (например, `mem_limit: 512m`). При резком всплеске нагрузки куча росла, GC не успевал сработать, и ядро Linux убивало процесс по OOM (**Exit Code 137**).

* **Решение (начиная с Go 1.19):**  
  Используйте переменную окружения **`GOMEMLIMIT`**:
  ```yaml
  services:
    app:
      mem_limit: 512m
      environment:
        - GOMEMLIMIT=450MiB # Оставляем ~10-15% запаса под стек и структуры рантайма
  ```
  При приближении к порогу 450 МБ сборщик мусора Go начнет внеплановую агрессивную очистку, гарантированно спасая сервис от `OOMKilled`.

### ❓ 5. Как из контейнера обратиться к сервису, запущенному на локальном хосте (Mac / Linux / Windows)?

* `127.0.0.1` или `localhost` внутри контейнера указывает **на сам этот контейнер**, а не на ваш ноутбук.
* **На macOS и Windows (Docker Desktop):**  
  Используйте специальное зарезервированное DNS-имя: **`host.docker.internal`**  
  (например: `POSTGRES_HOST=host.docker.internal`).
* **На чистом Linux:**  
  Добавьте сопоставление хоста в запуск:
  ```yaml
  # docker-compose.yml:
  services:
    app:
      extra_hosts:
        - "host.docker.internal:host-gateway"
  ```

### ❓ 6. Как безопасно скачивать приватные Go-модули без утечки токенов и SSH-ключей в Docker-образ?

* ❌ **Опасный антипаттерн:**  
  Использовать `ARG GITHUB_TOKEN=ghp_xxx` и сохранять его в `ENV`. Даже если удалить файл позже, токен навсегда останется в метаданных промежуточных слоев (`docker history`)!
* ✅ **Безопасный продакшен-стандарт (BuildKit Secret Mount):**
  ```dockerfile
  # В Dockerfile монтируем токен как виртуальный файл:
  RUN --mount=type=secret,id=gh_token \
      git config --global url."https://oauth2:$(cat /run/secrets/gh_token)@github.com/".insteadOf "https://github.com/" && \
      go mod download
  ```
  Сборка с передачей секрета из переменной хоста:
  ```bash
  docker build --secret id=gh_token,env=GITHUB_TOKEN -t my-app .
  ```
  Секрет монтируется только в оперативную память на время выполнения шага и **никогда не попадает в итоговый образ**.

### ❓ 7. Как вшить версию приложения и Git-хэш коммита в бинарник при сборке через Docker?

Используйте флаг компилятора `-ldflags -X`:

В коде Go (`cmd/app/main.go`):
```go
package main

var (
    version = "dev"
    commit  = "none"
)
```

В `Dockerfile`:
```dockerfile
ARG APP_VERSION=dev
ARG COMMIT_HASH=unknown

RUN CGO_ENABLED=0 go build \
    -ldflags="-s -w -X 'main.version=${APP_VERSION}' -X 'main.commit=${COMMIT_HASH}'" \
    -o /bin/wallet-app ./cmd/app
```

При сборке через Docker CLI:
```bash
docker build \
    --build-arg APP_VERSION=v1.2.0 \
    --build-arg COMMIT_HASH=$(git rev-parse --short HEAD) \
    -t wallet-app:v1.2.0 .
```

### ❓ 8. Почему сборка Docker на Mac (Apple Silicon) иногда занимает в 10 раз больше времени?

* **Причина:** Если в Dockerfile указан образ под архитектуру `linux/amd64` (Intel/AMD), Mac с процессором M1/M2/M3/M4 вынужден выполнять инструкции через тяжелый программный эмулятор **Rosetta 2 / QEMU**.
* **Как ускорить:**  
  1. Для локальной разработки всегда используйте нативные ARM64-образы (Docker выберет их автоматически).
  2. Если нужно собрать AMD64-бинарник для продакшена на своем Mac, используйте **кросс-компиляцию Go** (`GOARCH=amd64`), а не эмуляцию всего Docker-контейнера: компилятор Go делает это нативно со 100% скоростью процессора.

### ❓ 9. Как отлаживать Go-код внутри Docker-контейнера через Delve (Remote Debugging и точки останова)?

Частый сценарий локальной разработки: микросервис крутится в Docker Compose (вместе с базой PostgreSQL и Redis), вы ставите точку останова (красный кружок Breakpoint) прямо в строке кода в своей IDE (VS Code, GoLand, Antigravity, Cursor), отправляете HTTP-запрос и хотите, чтобы выполнение программы замерло на этой точке, позволяя проинспектировать значения переменных и сделать пошаговый переход (`F10`/`F11`).

Для работы удаленной отладки (Remote Debugging) необходима связка из 4 обязательных компонентов:

```
┌─────────────────────────────────┐                 ┌───────────────────────────────────────────────┐
│       ХОСТ-МАШИНА (IDE)         │                 │               DOCKER-КОНТЕЙНЕР                │
│                                 │                 │                                               │
│  [VS Code / GoLand / Cursor]    │  TCP :40000     │  [Отладчик Delve (dlv)]                       │
│  - Установка Breakpoint         │ ──────────────> │  - Режим: --headless --listen=:40000          │
│  - Панель переменных            │  (DAP Protocol) │        │                                      │
│  - substitutePath маппинг       │                 │        ▼ ptrace (SYS_PTRACE + seccomp)        │
│                                 │                 │  [Go Бинарник (-gcflags="all=-N -l")]        │
└─────────────────────────────────┘                 └───────────────────────────────────────────────┘
```

---

#### 🛠️ 4 обязательных правила настройки Remote Debugging:

1. **Флаги компиляции `-gcflags="all=-N -l"`:**  
   По умолчанию компилятор Go агрессивно оптимизирует код: удаляет неиспользуемые переменные и выполняет инлайнинг функций (встраивание тел функций вместо вызова). В результате в отладчике переменные показывают `<optimized out>`, а курсор хаотично перескакивает через строки. Флаги `-N` (отключить оптимизации) и `-l` (отключить инлайнинг) делают код 100% предсказуемым для отладчика.
2. **Отладчик Delve (`dlv`):**  
   Официальный стандартный отладчик для Go (`github.com/go-delve/delve/cmd/dlv`). В контейнере он запускается как TCP-сервер (`--headless --listen=:40000 --api-version=2 --accept-multiclient --continue`).
3. **Разрешения ядра Linux (`SYS_PTRACE` и `seccomp:unconfined`):**  
   Для перехвата инструкций процессора и остановки горутин отладчик использует системный вызов ядра **`ptrace`**. По умолчанию Docker блокирует его встроенным профилем безопасности seccomp. Без прав `cap_add: [SYS_PTRACE]` и `security_opt: [seccomp:unconfined]` Delve упадет с фатальной ошибкой `operation not permitted`.
4. **Сопоставление путей файлов (`substitutePath` / Path Mapping):**  
   *Главная ловушка новичков!* На хосте файл имеет путь `/Users/alex/projects/app/main.go`, а внутри контейнера он лежит в `/app/main.go`. Если не настроить сопоставление путей, IDE передаст отладчику путь хоста, Delve не сможет найти файл, и точка останова станет серой («unverified breakpoint / disabled») и никогда не сработает!

#### 📄 Готовые конфигурации (Copy-Paste)

##### 1. `Dockerfile.dev` (образ для локальной разработки и отладки):
```dockerfile
FROM golang:1.24-alpine

# Устанавливаем build-base (gcc) и git, необходимые для delve
RUN apk add --no-cache git build-base

# Устанавливаем отладчик Delve
RUN go install github.com/go-delve/delve/cmd/dlv@latest

WORKDIR /app

COPY go.mod go.sum ./
RUN go mod download

COPY . .

# Собираем бинарник с отключенной оптимизацией и инлайнингом
RUN CGO_ENABLED=0 go build -gcflags="all=-N -l" -o /bin/app-debug ./cmd/app

# 8080 — HTTP API, 40000 — порт удаленного отладчика Delve
EXPOSE 8080 40000

# Запускаем бинарник под управлением Delve в headless-режиме
CMD ["dlv", "--listen=:40000", "--headless=true", "--api-version=2", "--accept-multiclient", "--continue", "exec", "/bin/app-debug"]
```

##### 2. `docker-compose.dev.yml`:
```yaml
version: "3.8"

services:
  app:
    build:
      context: .
      dockerfile: Dockerfile.dev
    ports:
      - "8080:8080"     # Доступ к HTTP API
      - "40000:40000"   # Проброс порта отладчика Delve на хост!
    security_opt:
      - seccomp:unconfined # ⚠️ ОБЯЗАТЕЛЬНО: разрешаем системные вызовы ptrace
    cap_add:
      - SYS_PTRACE        # ⚠️ ОБЯЗАТЕЛЬНО: даем контейнеру права на отладку процессов
    volumes:
      - .:/app            # Монтируем локальный код внутрь контейнера
    environment:
      - DB_HOST=postgres
      - DB_PORT=5432
```

#### 🚀 Пошаговый сценарий отладки на практике

1. **Запустите контейнер в dev-режиме:**
   ```bash
   docker compose -f docker-compose.dev.yml up --build -d
   ```
   В логах контейнера (`docker compose logs -f app`) появится надпись:
   `API server listening at: [::]:40000`
2. **Поставьте точку останова в коде:**  
   Откройте нужный `.go` файл в IDE (например, `handlers.go`) и кликните левее номера строки (появится красный кружок Breakpoint).
3. **Подключитесь отладчиком из IDE:**  
   В панели **Run & Debug** выберите конфигурацию **`Docker: Attach to Go`** и нажмите **`F5`** (зеленый треугольник).  
   Внизу окна IDE панель окрасится в оранжевый цвет, и появится панель управления отладкой (`Continue`, `Step Over`, `Step Into`, `Stop`).
4. **Сделайте тестовый запрос:**
   ```bash
   curl http://localhost:8080/api/v1/users/123
   ```
5. **🎯 Точка останова сработала!**  
   Запрос в терминале замрёт. IDE автоматически выйдет на передний план и подсветит строку с брейкпоинтом. В левой панели вы увидите:
   - **Variables (Переменные):** текущие значения всех локальных переменных, аргументов функции и структур;
   - **Call Stack (Стек вызовов):** цепочку вызовов функций вплоть до `main()`;
   - **Goroutines:** список всех активных горутин.  
   Нажимайте **`F10`** (Step Over) для перехода на следующую строку или **`F5`** (Continue) для продолжения работы.

#### 💡 Продвинутый уровень: Автоперезапуск с отладкой (Air + Delve)

Если вы используете утилиту hot-reload **Air**, вы можете отлаживать приложение без необходимости вручную перезапускать контейнер при каждом изменении кода!

В конфигурации `.air.toml`:
```toml
[build]
  # Собираем с флагами отладки
  cmd = "go build -gcflags='all=-N -l' -o ./tmp/main ./cmd/app"
  bin = "./tmp/main"
  # Запускаем бинарник через Delve
  full_bin = "dlv exec ./tmp/main --headless=true --listen=:40000 --api-version=2 --accept-multiclient --continue"
```
При сохранении любого файла Air автоматически пересоберет проект и перезапустит Delve на порту `40000`, готовый к следующему подключению IDE.

## 9. Дорожная карта: Куда двигаться дальше

После уверенного владения связкой Docker + Docker Compose изучайте следующие технологии:

1. **Testcontainers-Go:**
   * Написание интеграционных тестов, которые прямо из `go test` автоматически поднимают временный контейнер с реальной базой данных и уничтожают его после завершения тестов. Подробнее: [Том 5: Раздел 17](05-go-core-testing-arch.md#17-интеграционные-тесты-с-testcontainers-go).
2. **CI/CD Пайплайны (GitHub Actions / GitLab CI):**
   * Автоматическая сборка Docker-образа по пушу в `master`, прогон тестов внутри контейнера и публикация в Docker Hub / GHCR с кэшированием слоев в GitHub Cache (`type=gha`).
3. **Оркестрация в продакшене (Kubernetes & Helm):**
   * Docker Compose предназначен для локальной разработки и небольших одиночных серверов.
   * Для масштабирования на кластер серверов, автоматического перезапуска при падении узлов и Rolling Updates (обновление без простоя) изучается **Kubernetes (K8s)**.
