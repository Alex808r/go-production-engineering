## 1. Выравнивание данных и Struct Padding

### Проблема:

В современных 64-битных CPU процессоры считывают память машинными словами (word) по 8 байт. Для обеспечения атомарности и максимальной скорости чтения компилятор Go выравнивает поля структур по границам их типа.

- Тип `int64` (8 байт) должен начинаться по адресу, кратному 8.
- Тип `int32` (4 байта) — по адресу, кратному 4.
- Тип `bool` или `byte` (1 байт) — по любому адресу.

Если поля в структуре расположены вразнобой, компилятор вынужден вставлять пустые байты (**padding**):

```go
// ❌ Неоптимальная структура: 24 байта в памяти!
type BadStruct struct {
    A bool  // 1 байт + 7 байт padding (чтобы B начался с адреса кратного 8)
    B int64 // 8 байт
    C bool  // 1 байт + 7 байт padding (чтобы структура целиком была кратна 8)
}
```

### Решение:

Упорядочивайте поля структуры **по убыванию их размера** (от больших к меньшим).

```go
// ✅ Оптимальная структура: 16 байт в памяти (экономия 33.3% памяти!)
type GoodStruct struct {
    B int64 // 8 байт
    A bool  // 1 байт
    C bool  // 1 байт + 6 байт padding в конце
}
```

> **Совет из практики Uber:**  
> Используйте линтер `fieldalignment` из пакета `golang.org/x/tools/go/analysis/passes/fieldalignment`, чтобы находить структуры с избыточным padding.
>
> 💡 **Прагматичный баланс:** Оптимизация выравнивания полей критически важна для структур, которые создаются миллионами (кэши, большие срезы, сетевые пакеты). Для единичных конфигурационных структур или DTO читаемость, смысловая группировка полей и контракты сериализации/cgo важнее экономии нескольких байт. Не применяйте массовый слепой `-fix` ко всем структурам проекта.

## 2. Ловушка удержания памяти при срезах

### Проблема:

Срез (slice) в Go — это заголовок из 24 байт (на 64-бит): `Data unsafe.Pointer`, `Len int`, `Cap int`.  
Если вы загрузили из базы данных или файла огромный срез (например, 10 000 000 элементов) и вернули подстроку `huge[:2]`, **весь массив на 10 млн элементов остается привязанным к ссылке `Data`** и сборщик мусора (GC) не имеет права его удалить!

```go
// ❌ Утечка памяти: удерживает весь массив huge в куче
func LeakSubslice(huge []int) []int {
    return huge[:2]
}
```

### Решение:

Для разрыва связи с исходным крупным массивом необходимо **скопировать данные в новый срез**:
- Начиная с Go 1.21 используйте `slices.Clone`:
- Либо явный `copy` в срез точной емкости:

```go
// ✅ Безопасно: выделяется новый независимый срез, GC освобождает массив huge
func SafeSubslice(huge []int) []int {
    return slices.Clone(huge[:2])
}
```

> [!WARNING]
> **Опасное заблуждение о срезе с тремя индексами (_Full slice expression_):**
>
> Конструкция `sub := huge[:2:2]` ограничивает `capacity` среза (`len=2, cap=2`) и защищает исходный массив от перезаписи при последующем `append`.
> Однако **она НЕ решает проблему удержания памяти**: указатель `sub.Data` по-прежнему ссылается на тот же самый базовый массив в памяти, и GC не сможет его освободить! Для изоляции данных и освобождения памяти **обязательно требуется копирование**.

## 3. Почему map никогда не уменьшается в памяти после delete

### Проблема:

Внутреннее устройство `map` в Go основано на массиве бакетов (`bmap`). Каждый бакет хранит до 8 пар ключ-значение.  
Когда в мапу добавляются миллионы элементов, рантайм аллоцирует тысячи бакетов. Но когда вы вызываете `delete(m, key)`:

1. Запись помечается как пустая.
2. Но **массив бакетов в структуре `hmap` НЕ сжимается и память не возвращается операционной системе**!

Если сервис в пике заполнил кэш на 2 ГБ, а затем удалил все ключи, процесс продолжит потреблять эти 2 ГБ RAM.

### Решение:

1. **Пересоздание мапы:** периодически или после массовой очистки пересоздавать мапу:
   ```go
   m = make(map[K]V) // старая мапа с бакетами уходит в GC
   ```
2. **Хранение указателей:** если значения крупные, храните `map[K]*V`, а не `map[K]V`. Тогда после `delete(m, k)` GC сможет освободить саму структуру `V`, хотя указатель в бакете останется.

## 4. Утечки таймеров в циклах: time.After против time.NewTimer

### Проблема:

Классическая ошибка в сетевых демонах и брокерах сообщений:

```go
// ❌ НЕЭФФЕКТИВНЫЙ КОД В ЦИКЛЕ
for {
    select {
    case msg := <-ch:
        handle(msg)
    case <-time.After(5 * time.Minute): // На КАЖДОЙ итерации создается новый таймер!
        log.Println("idle")
    }
}
```

- **Исторический контекст (до Go 1.23):** `time.After` привязывал объект таймера к внутреннему списку рантайма Go до истечения указанного срока (`time.Duration`). При высокой частоте событий создавалось множество таймеров, которые не могли быть удалены GC до момента своего срабатывания, что могло приводить к исчерпанию памяти (OOM).
- **Современный рантайм (Go 1.23+):** Новая семантика таймеров ([Go Wiki: Go123Timer](https://go.dev/wiki/Go123Timer)) действует при выполнении условий:
  1. Программа собрана компилятором Go 1.23 или новее;
  2. В `go.mod` основного модуля указана директива `go 1.23` или выше;
  3. Поведение не переопределено переменной окружения `GODEBUG=asynctimerchan=1`.
  В этом режиме неиспользуемые таймеры, на которые больше нет ссылок, становятся **доступными для сборки мусора (eligible for GC)** в очередных циклах GC, не дожидаясь наступления дедлайна. Каналы таймеров стали синхронными (unbuffered).
- **Почему `time.After` в цикле по-прежнему стоит избегать:** Даже с новым GC создание таймера на каждой итерации порождает постоянный поток аллокаций в куче (allocation churn), увеличивает нагрузку на планировщик и задержки GC. В горячих циклах переиспользуйте таймер, когда расходы на аллокации существенны. Для редких одиночных событий `time.After` вполне подходит и прямо допускается документацией Go.

### Решение:

В высоконагруженных циклах и сетевых обработчиках переиспользуйте один экземпляр `time.NewTimer`:

```go
// ✅ Безопасный и эффективный код (при go >= 1.23 в go.mod):
timer := time.NewTimer(5 * time.Minute)
defer timer.Stop()

for {
    timer.Reset(5 * time.Minute) // В Go 1.23+ Reset() сбрасывает таймер и синхронизирует канал
    select {
    case msg := <-ch:
        handle(msg)
    case <-timer.C:
        log.Println("idle")
    }
}
```

> [!NOTE]
> **Контракт time.Reset в Go < 1.23 (и тонкости дренажа канала):**
>
> До Go 1.23 официальный контракт [time.Reset](https://pkg.go.dev/time@go1.22.12#Timer.Reset) требовал вызывать `Reset()` **только на остановленном или просроченном таймере с предварительно вычитанным каналом**:
> - Если событие таймера уже было прочитано вызывающим кодом (например, в ветке `case <-timer.C:`), канал **уже пуст** — повторно вычитывать его нельзя.
> - Если событие ещё не прочитано, требовалось остановить таймер через `if !timer.Stop()`. Если `Stop()` вернул `false` (таймер успел истечь до вызова остановки), событие необходимо вычитать **блокирующим чтением `<-timer.C`**:
>   ```go
>   if !timer.Stop() {
>       <-timer.C
>   }
>   timer.Reset(d)
>   ```
>   ⚠️ Неблокирующий drain `select/default` здесь **небезопасен**: рантайм мог ещё не успеть завершить отправку события в канал в момент выполнения `select`, из-за чего устаревший тик оставался в буфере. Блокирующий `<-timer.C` гарантирует вычитку, но корректен строго при условии, что других параллельных получателей из этого канала нет. В Go 1.23+ этот сложный бойлерплейт устранён.

## 5. Kubernetes CPU Throttling и рантайм Go (automaxprocs)

### Проблема:

В контейнерах Kubernetes разработчик задает лимиты: `resources.limits.cpu: "2"`.  
Однако системный вызов `runtime.NumCPU()` в Go ничего не знает про CFS (Completely Fair Scheduler) квоты Linux cgroups! Он опрашивает ядро хоста и видит, например, все 64 ядра физического сервера.  
В результате:

- Go инициализирует `GOMAXPROCS = 64`.
- Рантайм создает 64 системных потока и планировщика `P`.
- Контейнер мгновенно сжигает свои CFS-квоты за первые миллисекунды расчетного окна (100ms CFS period).
- Ядро Linux жестко замораживает процесс (**CPU Throttling**), вызывая резкие спайки латентности p99 до сотен миллисекунд.

### Решение:

- **Для версий Go до 1.25:** Используйте библиотеку [`go.uber.org/automaxprocs`](https://github.com/uber-go/automaxprocs):
  ```go
  import _ "go.uber.org/automaxprocs"

  func main() {
      // automaxprocs считывает лимиты из cgroups (/sys/fs/cgroup)
      // и выставляет правильный GOMAXPROCS, исключая троттлинг.
  }
  ```
- **Начиная с Go 1.25:** Рантайм Go на Linux нативно учитывает квоты CPU cgroup и периодически обновляет `GOMAXPROCS` при их изменении ([Go 1.25 release notes](https://go.dev/doc/go1.25#runtime)). Внешняя библиотека в Go 1.25+ больше не требуется. Однако важно учитывать ограничения встроенного механизма:
  - Автоматическая подстройка отключается при явной установке переменной окружения `GOMAXPROCS` или вызове `runtime.GOMAXPROCS(n > 0)` в коде;
  - Поведение может быть принудительно отключено флагом `GODEBUG=containermaxprocs=0`.

## 6. Размер буфера каналов: правило Uber и обоснование ёмкости

### Правило:

> **По умолчанию ёмкость канала должна быть либо 0 (unbuffered), либо 1.**
> Любой другой размер буфера допустим только при наличии явного обоснования: как выбрана ёмкость, что защищает канал от переполнения под нагрузкой и как обрабатывается отказ (backpressure).

```go
// ✅ Рекомендуется по умолчанию:
ch := make(chan int)    // Небуферизированный канал: строгая синхронизация «передал-принял»
ch := make(chan int, 1) // Буфер размера 1: для сигналов отмены или одиночных уведомлений без блокировки отправителя
```

### Почему нельзя наугад ставить произвольный буфер (`make(chan T, 100)`):

1. **Маскировка медленных консьюмеров:** Буфер откладывает проблему, но не решает её: при стабильном превышении входящего потока над исходящим буфер неизбежно заполнится, и сервис либо заблокируется, либо упадет по памяти.
2. **Потеря данных при аварии:** Все сообщения, накопившиеся в буфере в момент перезапуска или падения пода, теряются.
3. **Когда допустим буфер > 1:**
   - Пакетная обработка или пул воркеров с математически рассчитанной пропускной способностью.
   - Сглаживание кратковременных микро-всплесков при условии наличия **явного механизма backpressure** (отклонение лишних запросов со статусом 429/503).

## 7. Проверка интерфейсов во время компиляции

### Проблема:

Если тип `MyHandler` не полностью удовлетворяет интерфейсу `http.Handler`, ошибка выяснится только в момент передачи аргумента в функцию, или вовсе в рантайме (если используется динамическое приведение типов).

### Решение (Uber Style Guide):

Добавляйте статическую проверку на этапе компиляции:

```go
type Runner interface {
    Run() string
}

type Service struct{}

func (s *Service) Run() string {
    return "ok"
}

// ✅ Проверка компилятором: если у Service изменится сигнатура метода Run,
// билд упадет прямо на этой строке. В рантайме аллокаций нет.
var _ Runner = (*Service)(nil)
```

## 8. Ловушка типизированного nil

### Классический баг Go:

В Go интерфейс под капотом состоит из двух машинных указателей:
`[type, data]`. Интерфейс равен `nil` **только тогда, когда и `type`, и `data` равны `nil`**.

```go
type CustomError struct{}

func (e *CustomError) Error() string { return "fail" }

func Run() error {
    var err *CustomError = nil // type = *CustomError, data = nil
    return err                 // Возвращается interface error: [type=*CustomError, data=nil]
}

func main() {
    err := Run()
    if err != nil { // ⚠️ УСЛОВИЕ ИСТИННО! Интерфейс НЕ равен nil!
        fmt.Println("Ошибка произошла, хотя err равен nil указателю!")
    }
}
```

### Правило:

**Функция, возвращающая интерфейс `error`, должна явно возвращать нетипизированный `nil`:**

```go
func Run() error {
    if failed {
        return &CustomError{}
    }
    return nil // ✅ Всегда возвращайте явный nil!
}
```

### Как проверить в рантайме, что внутри интерфейса лежит `nil`-указатель:

Если вызывающий код получил интерфейс `any` или `error` от внешнего пакета, проверить вложенный указатель можно двумя способами:

1. **Через Type Assertion или Type Switch (быстро, 0 аллокаций памяти):**

```go
func isNilPointer(i any) bool {
    switch v := i.(type) {
    case *string:
        return v == nil
    case *CustomError:
        return v == nil
    default:
        return i == nil
    }
}
```

2. **Через Reflection (универсально для любых ссылочных типов):**

```go
func isInterfaceDataNil(i any) bool {
    if i == nil {
        return true
    }
    v := reflect.ValueOf(i)
    switch v.Kind() {
    case reflect.Pointer, reflect.Slice, reflect.Map, reflect.Chan, reflect.Func, reflect.Interface:
        return v.IsNil()
    default:
        return false
    }
}
```

## 9. Паттерн Functional Options

### Почему он победил конструкторы с Config:

При создании сервисов часто требуется конфигурировать десятки параметров: порт, таймаут, размер пула, логгер, TLS.

- Конструктор `NewServer(host, port, timeout, maxConn, tls, logger)` ломает обратную совместимость при добавлении параметров.
- Структура `NewServer(cfg ServerConfig)` не позволяет отличить «дефолтное значение» от «пользователь явно передал 0 или false».

### Реализация Functional Options:

```go
type Option func(*ServerConfig)

func WithPort(port int) Option {
    return func(c *ServerConfig) {
        c.Port = port
    }
}

func WithTimeout(t time.Duration) Option {
    return func(c *ServerConfig) {
        c.Timeout = t
    }
}

func NewServer(host string, opts ...Option) *Server {
    cfg := ServerConfig{
        Host:    host,
        Port:    8080,            // Дефолт
        Timeout: 30 * time.Second, // Дефолт
    }
    for _, opt := range opts {
        opt(&cfg)
    }
    return &Server{cfg: cfg}
}

// Использование:
srv1 := NewServer("localhost")
srv2 := NewServer("0.0.0.0", WithPort(9090), WithTimeout(5*time.Second))
```

> [!TIP]
> **Когда применять Functional Options:**
>
> Паттерн Functional Options идеален для публичных пакетов, библиотек и компонентов со множеством (5+) опциональных настроек, где критична обратная совместимость API при добавлении новых флагов. Для простых внутренних сервисов с 1–3 зависимостями обычный конструктор `NewService(repo, logger)` или простая структура параметров `Config` значительно проще, нагляднее и не требуют бойлерплейта.

## 10. Вызов метода на nil-указателе и переприсваивание ресивера

### Проблема (Классическая задача с собеседований в BigTech):

Что произойдет при вызове следующего кода?

```go
type Node struct {
    val int
}

func (n *Node) Init() {
    n = &Node{val: 42} // ⚠️ Переприсваивание локальной копии ресивера!
}

func main() {
    var n *Node = nil
    n.Init()
    fmt.Println(n.val) // 💥 Паника? Выведется 42?
}
```

### Разбор работы рантайма:

1. **Вызов метода на `nil`-указателе в Go полностью легален!**  
   Метод в Go — это синтаксический сахар для функции первого порядка: `Init(n *Node)`. Инструкция `n.Init()` компилируется в передачу аргумента `n = nil`. Программа не падает при вызове метода, пока тело метода не пытается разыменовать `nil` (`n.val`).
2. **Семантика передачи ресивера:**  
   Даже если ресивер является указателем `(n *Node)`, сам адрес передается в метод **по значению (копируется значение указателя на стеке)**. Внутри `Init()` переменная `n` — это локальная копия адреса. Инструкция `n = &Node{val: 42}` меняет лишь эту локальную стековую переменную. Исходная переменная `n` в `main` **остается равной `nil`**!
3. **Строка `fmt.Println(n.val)` разыменовывает `nil`:**  
   Рантайм выбрасывает **`panic: runtime error: invalid memory address or nil pointer dereference`**.

### Правильные решения:

1. **Использовать конструктор (идиоматично для Go):**
   ```go
   func NewNode(val int) *Node {
       return &Node{val: val}
   }
   ```
2. **Инициализировать память ДО вызова метода (мутировать поля):**

   ```go
   func (n *Node) SetVal(v int) {
       n.val = v // мутирует память по существующему валидному адресу
   }

   n := &Node{}
   n.SetVal(42)
   ```

3. **Разыменовать указатель `*n` (если он гарантированно не nil):**
   ```go
   *n = Node{val: 42}
   ```

## 11. Недетерминированная паника в select с закрытыми каналами

### Проблема:

Что произойдет при выполнении следующего кода?

```go
ch := make(chan int, 1)
close(ch)

stopCh := make(chan struct{})
close(stopCh)

select {
case ch <- 1:
    fmt.Println("sent to ch")
case <-stopCh:
    fmt.Println("stop signal received")
}
```

### Разбор рантайма:

- Запись в закрытый канал (`ch <- 1`) вызывает **`panic: send on closed channel`**.
- Чтение из закрытого канала (`<-stopCh`) мгновенно возвращает **zero value** (`struct{}{}, false`) без блокировки.
- В момент входа в `select` **оба кейса готовы к выполнению одновременно**.
- **Случайный выбор планировщика:** Во избежание голодания (starvation) рантайм Go перед оценкой готовых веток перемешивает их псевдослучайным генератором (`runtime.fastrandn`).
- **Итог:** Результат недетерминирован! С вероятностью 50% программа напечатает `"stop signal received"`, а в 50% случаев — **упадет в панику в проде**!

> [!IMPORTANT]
> **Золотое правило закрытия каналов:**
> 1. Канал закрывает **единственный назначенный владелец после гарантированного завершения всех отправителей** (например, единственный продюсер или отдельный координатор после `wg.Wait()`). Никогда не закрывайте канал со стороны читателя.
> 2. **Все операции отправки (`ch <- v`) должны гарантированно завершиться ДО закрытия канала.**
> ⚠️ Популярное заблуждение: «Обернем `close(ch)` в `sync.Once`, и всё будет безопасно». `sync.Once` защищает только от повторного вызова `close`, но **никак не спасает от паники `send on closed channel`**, если параллельный продюсер всё ещё пытается отправить данные. Завершение всех писателей координируют через `sync.WaitGroup` или контекст.

## 12. Неблокирующий select с default и скрытая потеря данных (Silent Drop)

### Задача с собеседования (Касперский):

Что произойдет при выполнении следующей программы?

```go
ch := make(chan int, 2)
var wg sync.WaitGroup
wg.Add(1)

go func() {
    defer wg.Done()
    for val := range ch {
        fmt.Println(val)
        time.Sleep(500 * time.Millisecond) // Медленный консьюмер
    }
}()

for i := 0; i < 15; i++ {
    select {
    case ch <- i:
    default:
        // Если буфер полон — молча пропускаем
    }
}
close(ch)
wg.Wait()
```

### Анализ конкурентности и недетерминизма:

- **Почему результат недетерминирован:** Точное количество напечатанных сообщений зависит от планировщика рантайма Go и ОС: горутина консьюмера может запуститься до начала цикла, во время него или только после того, как основной поток заполнит буфер. Рассчитывать на фиксированный вывод (например, «ровно 0 и 1») исходя из тактов CPU в конкурентной среде нельзя.
- **Главная архитектурная угроза:** Как только буфер канала заполняется быстрым циклом продюсера, рантайм Go не ожидает освобождения места, а мгновенно переходит в ветку `default:`. В результате **отбрасываются сообщения, для которых отправка в момент выполнения `select` невозможна без блокировки** — причём молча и без уведомления вызывающего кода.

> [!CAUTION]
> **Архитектурный инвариант:**
>
> Паттерн `select + default` допустим только для некритичных данных (сброс логов, метрик, Load Shedding при отказе).
> **Никогда не отбрасывайте бизнес-сообщения (заказы, транзакции, задачи) через `default:`** без явного контракта отказа, возврата ошибки вызывающему коду или сохранения в Dead Letter Queue (DLQ).

## 13. Паттерн динамического отключения ветки select через nil-канал

### Механика:

В Go рантайм определяет строгие инварианты:

- Чтение из `nil`-канала (`<-ch`) $\to$ **вечная блокировка** (горутина засыпает навсегда).
- Запись в `nil`-канал (`ch <- v`) $\to$ **вечная блокировка**.

Внутри `select` заблокированная ветка просто исключается из опроса. Это дает элегантный паттерн динамического отключения вычитанных каналов:

```go
func MergeDrain(ch1, ch2 <-chan int) {
    for ch1 != nil || ch2 != nil {
        select {
        case v, ok := <-ch1:
            if !ok {
                ch1 = nil // ✅ Канал ch1 вычитан и закрыт — навсегда исключаем его из select!
                continue
            }
            fmt.Println("ch1:", v)

        case v, ok := <-ch2:
            if !ok {
                ch2 = nil // ✅ Канал ch2 вычитан и закрыт — навсегда исключаем его из select!
                continue
            }
            fmt.Println("ch2:", v)
        }
    }
    fmt.Println("Оба канала безопасно вычитаны без утечек и бесконечных циклов")
}
```

## 14. Идиома: «Принимай интерфейсы, возвращай структуры»

### Принцип (Accept interfaces, return concrete structs):

1. **Конструкторы возвращают конкретный указатель на структуру (`*Service`), а не интерфейс:**
   - Вызывающий код (consumer) сам решает, какие методы ему нужны, и объявляет **свой локальный минимальный интерфейс** (принцип ISP — Interface Segregation Principle).
   - Если объявлять гигантский интерфейс внутри самого пакета производителя, потребитель привязывается к жесткому контракту, лишаясь гибкости мокирования.
   - Возврат структуры избавляет рантайм от накладных расходов на создание интерфейсных объектов `iface` и снижает риск побега переменных в кучу (`escape analysis`).
2. **Функции и методы принимают интерфейсы:**
   - Это делает модуль независимым от конкретной реализации (Postgres, Mock, Redis, In-Memory) и обеспечивает 100% тестируемость.

```go
// ❌ Плохо: конструктор принудительно возвращает интерфейс производителя:
func NewUserRepository() UserRepository { return &userRepo{} }

// ✅ Идиоматично для Go:
// Пакет storage объявляет и возвращает конкретную структуру:
func NewUserRepo(db *pgxpool.Pool) *UserRepo { return &UserRepo{db: db} }

// А пакет domain / usecase объявляет интерфейс только с теми методами, которые ему нужны:
type UserReader interface {
    FindByID(ctx context.Context, id int64) (*User, error)
}
```

> [!NOTE]
> **Прагматичный баланс ([Go CodeReviewComments #interfaces](https://go.dev/wiki/CodeReviewComments#interfaces)):**
>
> Интерфейсы в Go вводятся на стороне потребителя (consumer-side) и только тогда, когда есть реальная потребность в полиморфизме или мокировании для тестов. Не создавайте интерфейсы «про запас» для каждого сервиса с единственной реализацией.
> *Исключения из возврата структуры:* возврат стандартных интерфейсов (`error`, `io.Reader`), фабрики с сокрытием внутренних реализаций или сохранение устоявшихся публичных контрактов библиотек.
