## 1. Выравнивание данных и Struct Padding

### Проблема:
В современных 64-битных CPU процессоры считывают память машинными словами (word) по 8 байт. Для обеспечения атомарности и максимальной скорости чтения компилятор Go выравнивает поля структур по границам их типа.
- Тип `int64` (8 байт) должен начинаться по адресу, кратному 8.
- Тип `int32` (4 байта) — по адресу, кратному 4.
- Тип `bool` или `byte` (1 байт) — по любому адресу.

Если поля в структуре расположены вразнобой, компилятор вынужден вставлять пустые байты (**padding**):

```go
// ❌ Неоптимальная структура: 24 байта в памяти!
type BadStruct struct {
    A bool  // 1 байт + 7 байт padding (чтобы B начался с адреса кратного 8)
    B int64 // 8 байт
    C bool  // 1 байт + 7 байт padding (чтобы структура целиком была кратна 8)
}
```

### Решение:
Упорядочивайте поля структуры **по убыванию их размера** (от больших к меньшим).

```go
// ✅ Оптимальная структура: 16 байт в памяти (экономия 33.3% памяти!)
type GoodStruct struct {
    B int64 // 8 байт
    A bool  // 1 байт
    C bool  // 1 байт + 6 байт padding в конце
}
```

> **Совет из практики Uber:**  
> Используйте линтер `fieldalignment` из пакета `golang.org/x/tools/go/analysis/passes/fieldalignment`, чтобы автоматически находить структуры с избыточным padding.

## 2. Ловушка удержания памяти при срезах

### Проблема:
Срез (slice) в Go — это заголовок из 24 байт (на 64-бит): `Data unsafe.Pointer`, `Len int`, `Cap int`.  
Если вы загрузили из базы данных или файла огромный срез (например, 10 000 000 элементов) и вернули подстроку `huge[:2]`, **весь массив на 10 млн элементов остается привязанным к ссылке `Data`** и сборщик мусора (GC) не имеет права его удалить!

```go
// ❌ Утечка памяти: удерживает весь массив huge в куче
func LeakSubslice(huge []int) []int {
    return huge[:2]
}
```

### Решение:
Начиная с Go 1.21 используйте `slices.Clone`, либо явный вызов `copy` в срез точной емкости:

```go
// ✅ Безопасно: GC освобождает исходный массив huge
func SafeSubslice(huge []int) []int {
    return slices.Clone(huge[:2])
}
```

Альтернатива с тремя индексами (*Full slice expression*):
```go
sub := huge[:2:2] // len=2, cap=2 (ограничивает capacity, защищая от случайного append в исходный массив)
```

## 3. Почему map никогда не уменьшается в памяти после delete

### Проблема:
Внутреннее устройство `map` в Go основано на массиве бакетов (`bmap`). Каждый бакет хранит до 8 пар ключ-значение.  
Когда в мапу добавляются миллионы элементов, рантайм аллоцирует тысячи бакетов. Но когда вы вызываете `delete(m, key)`:
1. Запись помечается как пустая.
2. Но **массив бакетов в структуре `hmap` НЕ сжимается и память не возвращается операционной системе**!

Если сервис в пике заполнил кэш на 2 ГБ, а затем удалил все ключи, процесс продолжит потреблять эти 2 ГБ RAM.

### Решение:
1. **Пересоздание мапы:** периодически или после массовой очистки пересоздавать мапу:
   ```go
   m = make(map[K]V) // старая мапа с бакетами уходит в GC
   ```
2. **Хранение указателей:** если значения крупные, храните `map[K]*V`, а не `map[K]V`. Тогда после `delete(m, k)` GC сможет освободить саму структуру `V`, хотя указатель в бакете останется.

## 4. Утечки таймеров в циклах: time.After против time.NewTimer

### Проблема:
Классическая ошибка в сетевых демонах и брокерах сообщений:
```go
// ❌ СКРЫТАЯ УТЕЧКА ПАМЯТИ
for {
    select {
    case msg := <-ch:
        handle(msg)
    case <-time.After(5 * time.Minute): // На КАЖДОЙ итерации создается новый канал!
        log.Println("idle")
    }
}
```
`time.After` возвращает канал `<-chan Time`, но сам объект таймера привязан к внутреннему списку рантайма Go до тех пор, пока не истечет указанное время (5 минут). Если в секунду приходит 10 000 сообщений, вы создадите 10 000 таймеров в секунду, которые будут висеть в памяти 5 минут, приводя к OOM.

### Решение:
Используйте `time.NewTimer` с обязательным `defer timer.Stop()` либо переиспользуйте один таймер с `Reset()`:

```go
// ✅ Безопасный код:
timer := time.NewTimer(5 * time.Minute)
defer timer.Stop()

for {
    timer.Reset(5 * time.Minute)
    select {
    case msg := <-ch:
        if !timer.Stop() {
            <-timer.C // Очищаем канал, если таймер успел сработать
        }
        handle(msg)
    case <-timer.C:
        log.Println("idle")
    }
}
```

## 5. Kubernetes CPU Throttling и рантайм Go (automaxprocs)

### Проблема:
В контейнерах Kubernetes разработчик задает лимиты: `resources.limits.cpu: "2"`.  
Однако системный вызов `runtime.NumCPU()` в Go ничего не знает про CFS (Completely Fair Scheduler) квоты Linux cgroups! Он опрашивает ядро хоста и видит, например, все 64 ядра физического сервера.  
В результате:
- Go инициализирует `GOMAXPROCS = 64`.
- Рантайм создает 64 системных потока и планировщика `P`.
- Контейнер мгновенно сжигает свои CFS-квоты за первые миллисекунды расчетного окна (100ms CFS period).
- Ядро Linux жестко замораживает процесс (**CPU Throttling**), вызывая резкие спайки латентности p99 до сотен миллисекунд.

### Решение (стандарт Uber):
Используйте библиотеку [`go.uber.org/automaxprocs`](https://github.com/uber-go/automaxprocs):
```go
import _ "go.uber.org/automaxprocs"

func main() {
    // automaxprocs автоматически считывает лимиты из cgroups (/sys/fs/cgroup)
    // и выставляет правильный GOMAXPROCS, исключая троттлинг.
}
```

## 6. Размер буфера каналов: золотое правило Uber

### Правило:
> **Размер емкости канала должен быть либо 0 (unbuffered), либо 1.**

```go
// ✅ Рекомендуется:
ch := make(chan int)    // Небуферизированный канал: строгая синхронизация
ch := make(chan int, 1) // Буфер размера 1: для сигналов отмены или одиночных уведомлений
```

### Почему нельзя наугад ставить `make(chan T, 100)`:
1. Произвольный размер буфера маскирует race conditions и медленные консьюмеры.
2. При падении сервиса сообщения, застрявшие в буфере, теряются.
3. Единственное исключение: специализированные пулы воркеров с математически доказанной емкостью и явным backpressure.

## 7. Проверка интерфейсов во время компиляции

### Проблема:
Если тип `MyHandler` не полностью удовлетворяет интерфейсу `http.Handler`, ошибка выяснится только в момент передачи аргумента в функцию, или вовсе в рантайме (если используется динамическое приведение типов).

### Решение (Uber Style Guide):
Добавляйте статическую проверку на этапе компиляции:

```go
type Runner interface {
    Run() string
}

type Service struct{}

func (s *Service) Run() string {
    return "ok"
}

// ✅ Проверка компилятором: если у Service изменится сигнатура метода Run,
// билд упадет прямо на этой строке. В рантайме аллокаций нет.
var _ Runner = (*Service)(nil)
```

## 8. Ловушка типизированного nil

### Классический баг Go:
В Go интерфейс под капотом состоит из двух машинных указателей:
`[type, data]`. Интерфейс равен `nil` **только тогда, когда и `type`, и `data` равны `nil`**.

```go
type CustomError struct{}

func (e *CustomError) Error() string { return "fail" }

func Run() error {
    var err *CustomError = nil // type = *CustomError, data = nil
    return err                 // Возвращается interface error: [type=*CustomError, data=nil]
}

func main() {
    err := Run()
    if err != nil { // ⚠️ УСЛОВИЕ ИСТИННО! Интерфейс НЕ равен nil!
        fmt.Println("Ошибка произошла, хотя err равен nil указателю!")
    }
}
```

### Правило:
**Функция, возвращающая интерфейс `error`, должна явно возвращать нетипизированный `nil`:**
```go
func Run() error {
    if failed {
        return &CustomError{}
    }
    return nil // ✅ Всегда возвращайте явный nil!
}
```

## 9. Паттерн Functional Options

### Почему он победил конструкторы с Config:
При создании сервисов часто требуется конфигурировать десятки параметров: порт, таймаут, размер пула, логгер, TLS.
- Конструктор `NewServer(host, port, timeout, maxConn, tls, logger)` ломает обратную совместимость при добавлении параметров.
- Структура `NewServer(cfg ServerConfig)` не позволяет отличить «дефолтное значение» от «пользователь явно передал 0 или false».

### Реализация Functional Options:
```go
type Option func(*ServerConfig)

func WithPort(port int) Option {
    return func(c *ServerConfig) {
        c.Port = port
    }
}

func WithTimeout(t time.Duration) Option {
    return func(c *ServerConfig) {
        c.Timeout = t
    }
}

func NewServer(host string, opts ...Option) *Server {
    cfg := ServerConfig{
        Host:    host,
        Port:    8080,            // Дефолт
        Timeout: 30 * time.Second, // Дефолт
    }
    for _, opt := range opts {
        opt(&cfg)
    }
    return &Server{cfg: cfg}
}

// Использование:
srv1 := NewServer("localhost")
srv2 := NewServer("0.0.0.0", WithPort(9090), WithTimeout(5*time.Second))
```

## 🎯 Сводная таблица ловушек и решений

| Подводный камень | Чем грозит | Правильное решение |
| :--- | :--- | :--- |
| **Неупорядоченные поля структуры** | +30-50% перерасход RAM на padding | Сортировать поля от больших к меньшим; линтер `fieldalignment` |
| **Reslicing большого массива** | Утечка гигабайтов памяти через `Data` ptr | `slices.Clone()` или `huge[:n:n]` |
| **`delete()` из map** | Память бакетов не возвращается GC | Пересоздавать мапу `m = make(...)` или хранить указатели |
| **`time.After` внутри `select` цикла** | OOM из-за тысяч неудалившихся таймеров | `time.NewTimer` с `defer timer.Stop()` и `Reset()` |
| **Рантайм Go в Kubernetes** | CFS CPU Throttling, деградация p99 latency | Библиотека `go.uber.org/automaxprocs` |
| **Большие буферы каналов** | Маскировка гонок данных, утечка сообщений | Буфер 0 или 1; очереди только с явным backpressure |
| **Типизированный `nil` в `error`** | Ложное срабатывание `if err != nil` | Возвращать чистый `nil`, а не типизированную переменную |
| **Проверка интерфейсов** | Ошибки типизации только в рантайме | `var _ Interface = (*Type)(nil)` |
